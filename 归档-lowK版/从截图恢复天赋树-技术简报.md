## 四、已经做到哪一步

1. **亮点检测**（脚本 `/tmp/v2/nodecluster.swift`，已编译为 `/tmp/nodecluster`）
   在图上找出「发光的大节点」：亮度 >0.45、饱和度 >0.18、连通域 ≥25px。
   结果（图13，10 个）：
   ```
   (328,135) (419,176) (629,177) (1072,297) (536,329)
   (1046,368) (895,439) (736,466) (797,524) (855,583)
   ```
   图23 也是 10 个，图15 是 10 个，图14 是 7 个，图16 是 3 个。

2. **精度**：相邻亮点间距 **75~525 像素**；节点图标本身 20~33 像素。
   所以「检测」不是瓶颈——瓶颈是**只能检测到大的亮点**（约 10 个/图），
   而整棵树有 120+ 个节点，其中大量是过路小点（属性和小天赋），在图上只有几个像素。

3. **踩过的坑（别再踩）**
   - `/tmp/tree_nodes_xy.json` 里**很多节点共用同一个坐标**（group 中心坐标），
     因为节点的真实位置 = group 坐标 + 轨道半径 × 角度，JSON 里给的是 group 坐标。
     直接拿它做几何匹配会退化（4476 个节点只有 1362 个不同坐标）。
     **必须先按 `orbit` / `orbitIndex` 算出节点的真实坐标**，再匹配。
     半径值在 `tree05.json` 的 `constants` 里（找 `orbitRadii` / `orbitRadius`）。
   - 验证方向不能搞反：应该是「树节点→投到像素→看有没有落在亮点上」，
     写成「亮点→投到树坐标→找最近节点」会退化成恒等变换、全是假阳性。

## 五、可行路线（按推荐顺序）

### 路线 A：先算真实坐标，再做 RANSAC 匹配
1. 用 `constants.orbitRadii` + `node.orbit` + `node.orbitIndex` 把每个节点换算成真实 (x,y)
2. 用 2 对亮点↔节点求相似变换（含翻转），RANSAC 验证其余亮点
3. 得到 10 个大节点的身份后，**沿 `connections` 走最短路径把它们连起来**——
   这才是作者真正点过的树（游戏里已点节点必须连通）
4. 输出的节点集合先和「点数 = 等级-1+任务点」核对：90 级约 113 点、95 级约 118 点

### 路线 B：PoB 导出（最稳，5 分钟）
1. 打开 PoB2 → Import/Export 页 → 「Export to in-game build planner」
2. 填 Build name → 点 **Export Selected Sets** → 点 **Open Folder**
3. 把那个 `.build` 发过来；本机已有流水线 `/tmp/v2/ingest_build.py`：
   ```
   python3 /tmp/v2/ingest_build.py <来源.build> day2
   ```
   它会：校验 passives/技能的 ID、把 ascendancy 转成 `Ranger1`、生成站点用的两个文件名、
   打印体检报告。**这条路的产物 100% 准确。**

### 路线 C：从他角色页拿（不用装 PoB）
`https://poe.ninja/poe2/profile/Kommmm-0462/forbiddenrites/character/网瘾老年人冰射`
右上角 **Build Planner** 按钮 → 下一个 `.build` → 交给路线 B 的脚本。
